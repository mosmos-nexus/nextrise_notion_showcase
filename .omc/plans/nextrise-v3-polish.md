### Contested Decisions — Options ≥2

#### SD-A — Restructure approach (build-split vs in-file modules)

- **Option A1 (CHOSEN) — `src/` partials + `scripts/build.mjs` deterministic concat → emits single `index.html`.**
  Split by cohesion/coupling: `src/styles/*.css` (base/tokens, then one file per section S0–S6 + cross-cutting starfield/bloom/print/reduced-motion), `src/slides/*.html` (one partial per slide or per section), `src/js/*.js` (engine core, pan, iframe, starfield, counters/typewriter, boot). `build.mjs` concatenates in a fixed manifest order, injects ONE `GENERATED — edit src/, run npm run build` banner as an **HTML comment at the top of `<head>` ONLY**, and writes `index.html`. A **stale-check** (`build.mjs --check`) rebuilds to a temp buffer and asserts it equals the committed `index.html` byte-for-byte (exit 1 on drift).
  - **EXPORT-SURFACE CONSTRAINT (verified — A1 modified by Critic):** `saveFile()` (index.html:2165) serializes `document.documentElement.outerHTML` and is reachable from BOTH edit-mode Ctrl+S (:1928) and normal-mode Ctrl+S (:1931) — so the runtime DOM is itself a shippable artifact. Therefore: (a) build emits exactly ONE GENERATED banner (HTML comment at top of `<head>` only); (b) `@@include` provenance markers are **STRIPPED from the emitted output** — they live in `src/` only, because traceability belongs in `src/`, NOT in the artifact, and any marker in the DOM would survive a Ctrl+S export and pollute the exported file; (c) the Ctrl+S-exported deck is a **TERMINAL artifact** — it is NEVER re-fed to `build.mjs` (export is downstream of build, not an input). This guarantees a second export shows no banner duplication.
  - Pros: real cohesion/coupling boundaries (the §2 directive); each defect WP edits a focused partial not a 2762-line file; drift-guard is enforceable in CI/pre-commit; single-file deliverable preserved by construction (build output IS the deliverable, and a Ctrl+S re-export of it is clean). Honors P4: the FIRST build must emit an index.html behaviorally identical to today's.
  - Cons: introduces Node tooling + a build step (the `file://` workflow now requires `npm run build` before opening — but the OUTPUT still opens at `file://`); concat must be byte-deterministic (no formatter reordering, stable include order, LF endings); the equivalence gate (WP-R) is mandatory and non-trivial; WP-R is **hard time-boxed to 1 working day** with a binary abandon-to-monolith trigger (see status block / WP-R / ADR).

- **Option A2 (REJECTED) — In-file module organization only (section banners + folding, no build).**
  Keep one file; improve internal structure with clearer region comments and a documented section index.
  - Pros: zero new tooling; `file://` workflow unchanged; zero equivalence risk.
  - Cons: does NOT satisfy the directive ("split the monolith into component source files … WITH a build step"); 2762 lines stays the edit surface; no real coupling reduction. **Rejected:** fails the explicit user directive; the monolith edit-risk that motivated v3 maintainability work persists.

- **Why A1 over A2:** the directive is explicit about source files + a build step + a drift guard. A2 is the no-op. A1's only real risk (build/source desync) is exactly what the stale-check + first-build equivalence gate neutralize. **Honesty note (now clock-bound):** WP-R is hard time-boxed to **1 working day** with a **binary** abandon trigger — if `build.mjs` + the first-build equivalence walk + the E12 export round-trip are not ALL green by end of day 1, the fallback fires immediately: freeze `src/` on the branch, `git checkout index.html`, land D1–D8 directly in the monolith, revisit the split post-06-18 (DD1 > DD3). WP-R is gated AND time-boxed, never open-ended.

#### SD-B — D2 camera-zoom redesign technique (extend pan controller vs new zoom-stage component)

- **Option B1 (CHOSEN) — Extend the existing s2c pan controller into a per-zone crop-zoom + HTML-callout sequencer.**
  The current controller (`index.html:2193+`) already owns: the waypoint array `[146,381,547,762,1002,1184]` (source px, 1474×1218), the `srcYToTranslate` geometry math, `computeGeometry`, `animatePan`, the abort/pause machinery, and the `deck.pan.toggle` + `P`-key wiring + `registerHook('s2c')` lifecycle. v3 changes the *motion* at each MAPPED waypoint from "translateY + subtle 1.04 scale hold" to "translateY to center the zone + crop-zoom to ~1.6–2.0× scale on that zone" and, per mapped waypoint, animates in ONE HTML callout chip (white card, dark text, yellow accent). **The callout chips are AUTHORED IN THE DOM (always present in `src/slides/s2c.html`), rendered INSIDE `.pan-wrap` (the clip-testable element), and JS only animates them in.** The baked yellow SVG annotations are masked/ignored (the chip replaces them); since the source SVG is dark-themed, the zoomed crop has its own contrast.
  - **CLIP BOUNDARY (corrected — A5 + Critic Major#2, verified against index.html):** the crop-zoom clip boundary is **`#s2c .pan-wrap{overflow:hidden}` (index.html:476–477)**, NOT `.pan-inner`. `.pan-inner` (:480–482) is the *transformed* element; `.pan-wrap` is its clipping ancestor. Callout chips must live inside `.pan-wrap` so they are clip-testable at zoom. Under reduced-motion (`@media (prefers-reduced-motion:reduce)` :485–489), `.pan-wrap{overflow:visible}` + `.pan-inner img{object-fit:contain}` shows the whole SVG statically (the static contain view :486–488) and the controller's reduced-motion branch (:2194–2197 `deck.pan.toggle=function(){};return;` — a verified no-op) means **chips must show STATICALLY with that static contain view, no zoom.**
  - Pros: reuses all proven geometry + pause/abort/reduced-motion/`P`-key plumbing (P4); the waypoint→callout-text mapping is a pure data addition; smallest mechanism change; the wp4-exec.md DESCENDING sort lesson and pan-stop math are already correct and stay; DOM-authored chips degrade trivially under reduced-motion (already present, just not animated).
  - Cons: scale-zoom needs a transform-origin per zone (currently the controller only translates uniformly + scales about center); callout chip positioning must be authored per zone; "crop-zoom" means `.pan-wrap`'s `overflow:hidden` must hide the rest of the tall image at zoom (verify it clips at scale>1); the annotation→waypoint mapping cannot be grepped (see CHIP MAPPING below) — it is a render-time visual-read task.

- **Option B2 (REJECTED) — New standalone "zoom-stage" component (fresh crop-zoom engine, retire the pan controller for s2c).**
  - Pros: clean per-zone camera abstraction; could be reused by other slides.
  - Cons: throws away the proven abort/pause/`P`-key/reduced-motion/geometry code; re-introduces every solved bug (the DESCENDING-sort and onload-recompute lessons from wp4-exec.md); larger review surface on a 7-day clock; s3b also depends on `deck.pan.toggle` (it wraps `origPanToggle` at `:2665`) — retiring the controller forces a parallel s3b rework. **Rejected:** violates P4/P5; no defect requires a new component; the existing controller is one transform-origin + one callout layer away from satisfying D2.

- **Why B1 over B2:** D2 is a *motion + readability* change, not an architecture gap. The controller already centers zones and holds; adding transform-origin + zoom magnitude + a callout layer is an extension, not a rebuild. s3b's dependency on `deck.pan.toggle` makes a retirement actively risky.
